## Problema

O fact `persistence.provider` saiu `prisma-client-js`. O schema real tem `generator client { provider = "prisma-client-js" }` antes de `datasource db { provider = "postgresql" }`. A regra se chama `datasource-provider`, mas a regex pegava o primeiro `provider` do arquivo. O teste da suíte só tinha o bloco `datasource`, então não pegava o caso comum.

## Correção genérica

`prismaDatasourceProvider` lê só o bloco `datasource`. A fixture do teste passou a declarar o generator antes do datasource e continua exigindo `postgresql`. Nada foi especial para o nome Síndico Pro.

## Auditoria pré-commit

A implementação inicial passou a suíte e este dogfood. A auditoria adversarial seguinte, em fixtures sintéticas, encontrou um escape: `RepositoryView` conferia o path lexical e ainda lia através de um diretório symlink. `readText("src/main.ts")` e `list("src/modules")` podiam alcançar conteúdo e nomes fora do repository. A correção resolve o caminho real e recusa o que cair fora. Os dois snapshots acima não foram reescritos por essa correção.

A mesma auditoria mostrou binding JSON inválido tratado como ausente, o que permitia criar outra identidade, e `previousSnapshotId` apontando para snapshot inexistente ainda carregando o projeto. Os dois casos agora falham fechado, sem reparo automático. Renomear o checkout e onboardar o path novo continua criando outro `projectId`: não há sinal forte que autorize reassociação sem um `project bind`, que permanece fora da v0.8.
