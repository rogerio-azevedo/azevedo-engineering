- Azevedo Engineering: `0.6.1`
- Specification: `spec-sindico-pro-controle-de-encomendas-09bcb02b`
- Resultado de preparação coordenada: `READY`
- Resultado terminal das duas execuções: `BLOCKED` por lint global pré-existente
- Mutation: apenas em worktrees isoladas; sem commit, push, merge ou deploy nos targets

O dogfood comprovou a correção principal da v0.6.1: a mesma Specification de 17 critérios que a v0.6 não conseguia transformar em scope executável chegou a readiness coordenado, criou isolamento e recebeu implementação real. O resultado final, porém, não é `Done`: os linters globais obrigatórios já estavam vermelhos fora do scope autorizado. O harness preservou essa verdade em vez de declarar conclusão com base apenas em build e testes direcionados.

## B. Greenfield Exploration

10. **Detecção.** Ausência de símbolo/entry flow da própria feature, combinada com acceptance criteria completos e capabilities inferíveis, produz `greenfield-feature`; evidência estrutural direta produz `existing-feature`; casos inconclusivos ficam `uncertain`.

11. **Mudança de estratégia.** Existing-feature segue símbolo → entry point → flows → consumers/tests. Greenfield segue acceptance criteria → capabilities → integration surfaces → padrões arquiteturais → boundaries propostos.

12. **Derivação das surfaces.** Termos e regras dos ACs são mapeados para capabilities genéricas; arquivos só integram uma surface quando evidenciam aquela capability por estrutura/configuração/contrato e recebem IDs de evidência.

13. **Candidate versus substantive.** Match lexical cria candidate. Scope substantivo exige basis como `architectural-pattern`, `acceptance-criterion-match`, relação de contrato, import/flow ou símbolo direto, além de evidência citável.

14. **Scope de arquivo novo.** Greenfield autoriza boundary de diretório/módulo ainda inexistente quando a convenção está comprovada por implementações existentes e ligada a ACs e integration surfaces. Não autoriza um filename inventado só por similaridade verbal.

15. **Stop conditions.** Existing-feature precisa de entry flow defensável; greenfield pode parar com surfaces suficientes, boundaries propostos, coverage planejável, verification real e unknowns explícitos. Product decision obrigatória, scope fraco ou capability mandatória indisponível bloqueia.

## C. Relevance

16. **Falso positivo lexical.** Scores lexicais priorizam inspeção, mas não promovem paths. `create-address` e outros candidatos semelhantes permaneceram excluídos do scope autorizado quando faltou relação estrutural.

17. **Entry point.** Só é validado por símbolo/manifest/framework boundary e flow observável. Encomendas ficou corretamente sem entry point existente nos dois projetos.

18. **Affected path.** Requer basis, evidence IDs e relação com ACs. Readiness recusa scope composto apenas de candidates.

19. **Testes.** `direct` exige import/relação com path ou contrato substantivo; `analogous` e `infrastructure` preservam utilidade sem alegar cobertura direta. O teste de IA/ocorrências deixou de ser `direct` e foi classificado `infrastructure`; frontend registrou `capability-unavailable`.

## E. Verification

25. **Capability versus requirement.** Capability descreve comando realmente disponível; requirement registra se aquela capability é necessária para provar a task. A ausência continua visível sem ser automaticamente blocker.

26. **Quando ausência bloqueia.** Quando uma regra/AC exige explicitamente a evidência indisponível ou quando não sobra nenhum meio legítimo de provar o comportamento obrigatório.

27. **Quando não bloqueia.** Backend sem script `typecheck` e frontend sem `test`/`typecheck` não bloquearam a preparação, pois não eram requirements. Nenhum `package.json` dos targets foi alterado para ensinar o projeto a passar.

28. **Command safety.** Allowlist de package scripts, argumentos seguros, containment, proibição de comandos destrutivos, no secrets e no commit/push foram preservados.

## K. Avaliação

70. **Problemas corrigidos.** Greenfield não exige símbolo inexistente; candidates não viram scope; testes lexicais não são direct; busca é adaptativa; verification segue capabilities; blocked pipeline é representável; intenção cross-repo é única; scope tem provenance; isolamento é posterior a READY; e core context não é silenciosamente truncado.

71. **Problemas que permaneceram.** Exploration ainda consome o budget inteiro nos dois projetos; regras heurísticas de capability podem coletar candidates demais; não há runtime de review/security nem verificação end-to-end; test/typecheck ausentes continuam lacunas técnicas.

72. **Novos problemas observados.** Required lint global pode tornar a execução terminalmente bloqueada por dívida pré-existente não atribuível ao change. Além disso, scripts de lint mutáveis são perigosos como verifiers: `npm run lint -- --no-fix` não neutraliza um `--fix` já embutido. O Azevedo precisa distinguir baseline/delta e declarar/verificar non-mutating commands antes de execução.

73. **Contexto para o Coding Agent.** Sim. O contexto apontou boundaries corretos, patterns de Prisma/Nest/GraphQL/Next, auth, upload, mail, audit e verification; a implementação coube quase integralmente no scope previsto. A única expansão foi o contrato GraphQL versionado e teve evidência.

74. **Onde o harness atrapalhou injustificadamente.** O gate de lint global bloqueou o estado terminal mesmo com changed-file lint, build e testes verdes, porque não existe ainda baseline/delta de qualidade. Também houve custo duplicado de Specification nos contexts project-specific e candidates amplos demais, embora o budget core tenha evitado perda de requisitos.

75. **Limitações conhecidas.** Sem E2E/DB test, reviewer, security reviewer, baseline-aware verification, detector de scripts mutáveis, provider runtime, PR/commit/deploy automation, shared-context deduplication ou continuous learning. A feature deve ser auditada e ganhar verificação integrada antes de merge.

## Veredito

A v0.6.1 respondeu melhor à pergunta central: o Coding Agent recebeu mais contexto, disciplina e evidência e conseguiu produzir a primeira feature cross-repo isolada. O sistema também disse a verdade no fim: implementação não equivale a conclusão. O cleanup acidental do checkout principal foi concluído; antes de considerar a feature pronta para merge, ainda é necessário auditar os diffs e adicionar evidência integrada para os critérios não verificados.
